A plain merge is safe and was used instead.

## #532 — current state and what's left

**Design**: done (Opus pass), `docs/design/532_hybrid_summary_synthesis_plan.md` (now merged into this branch). Re-analysis of the prior "arm (d)" measurement found the reported −27.7pt quote-fidelity drop was mostly a grading artifact (corrected: 0.909 vs 0.875 once #976's fix + two more tolerances are applied); the real, smaller coverage regression (−17pt, wide CI) was traced to a specific mechanism (the model answers from *uncitable* abstractive overview content because of an existing prompt rule) rather than treated as unexplained noise.

**Implementation + no-GPU verification**: DONE, merged into this branch (was `v0.6.0-hybrid-summary` worktree, now cleaned up). Covers: the hybrid composition logic (structured abstractive summary + verbatim closing digest section, replacing the old 3-section structure), a new `chat.rag.map_tier_hybrid` flag (experimental=True, gated behind `map_tier_summaries` also being on), a mandatory citation guard (`_guard_hybrid_overview_citations` in `service.py`) that suppresses citability on hybrid entries since their closing section is verbatim but not machine-attributable, Phase 0's REAL no-GPU oracle check against the full 137-file corpus (confirmed the design choices — did not overturn them: closing-section choice held, items-included beat lead-only by +111 recalled items, the K0 stop-ship rule did not trigger, hybrid beat control 3.4x on per-file coverage and 6.8x on pooled recall), and 137/137 new tests passing with genuine red-first verification via `git archive HEAD` scratch trees. Two decisions locked in and applied:
- Quote-fidelity reporting: strict original metric kept as primary and unchanged; the #976-corrected tolerant version added as a labeled secondary column (`quote_fidelity_tolerant`) — never silently swapped.
- `sections_budget`'s defect: out of scope for this branch, filed as #992 (see above).

**Explicitly NOT done, deferred by David's decision (2026-09-23)**: the GPU validation run (4-5 arms: control / arm-d re-run / hybrid / hybrid+citable-overview / control-again, ~130-turn expanded question set + two 81-turn AMI-81 legs). Estimated ~13h at `--concurrency 1`, ~6.5-7h at `--concurrency 2` (accepted for quality metrics, though it makes latency non-comparable — the plan's fallback is to take the latency guard from the `--concurrency 1` AMI-81 legs only).

**Why deferred**: GPU 2 has real contention right now — `openprocessor`'s own `triton-server` (long-running) plus what looks like their own active `vllm-gemma4-e4b` testing (a fresh container, ~18.76GB, started independently of this work), leaving only ~13.6GB free at last check. Needs coordination with whoever runs openprocessor's testing (or a wait for a clear window) before spending GPU time on this measurement. GPU 1 (project's primary card, 12GB) was considered but is likely too small for gemma-4-e4b at the 60k-token context lengths this measurement needs.

**To resume**: once GPU 2 capacity is confirmed clear (or a coordinated window is agreed), run the GPU validation exactly as `docs/design/532_hybrid_summary_synthesis_plan.md` section 5 specifies (arm order C1→D→H→C2, optionally H+a as a 5th arm, David already approved adding it).
