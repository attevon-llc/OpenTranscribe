4. Post-Transcription Enrichment explorable docs-site candidate: "what happens after transcription"

What the Transcription Pipeline's last step ("Post-process") fans out into: voiceprinting, gender/age detection, LLM speaker-ID suggestions, summarization, topic extraction, and analytics — all dispatched independently right after finalize.

Answers your voiceprint/fingerprint question directly: this already works for cloud ASR today. Local ASR gets embeddings inline from PyAnnote's native centroids; cloud ASR (no native centroids available) dispatches a dedicated extract_speaker_embeddings_task on the CPU queue instead — same outcome, different path. See tab 5 for the cloud-ASR-specific view of this.

5. Cloud ASR + Voiceprinting explorable docs-site candidate: "cloud ASR providers"

8 cloud providers (AssemblyAI, AWS, Azure, Deepgram, Gladia, Google, OpenAI, Speechmatics) sit behind one factory. Some return their own speaker labels; providers that don't still get local PyAnnote diarization on the downloaded audio. Either way, voiceprinting/fingerprinting happens — see the card in the diagram for the exact task name and why it's CPU, not GPU.

6. Speaker Clustering & Naming explorable docs-site candidate: "how speaker identification works"

What happens to a voiceprint after extraction: automatic matching against known profiles above a confidence threshold, or — for no confident match — grouping into cross-file clusters that wait for a human to merge, split, verify, and promote to a named, reusable profile.

9. Frontend Module Map explorable docs-site candidate: "frontend architecture"

Hand-curated from the real directory listing, because the automated tools (madge, dependency-cruiser) couldn't reliably trace this codebase's Svelte imports — see the root-cause writeup below the diagram if you want the details. This is the useful replacement.

Real circular dependency found, but already mitigated: lib/axios.ts → stores/auth.ts → lib/axios.ts. Checked the actual code: axios.ts uses await import('../stores/auth') (dynamic import) specifically to break the cycle at runtime. madge can't distinguish static from dynamic imports, so it flags a cycle that isn't live. Not a bug — no action needed.
Why the raw dependency-graph tools failed here (root cause, confirmed): frontend/node_modules was fine, but neither tool had a generated .svelte-kit/tsconfig.json to resolve the $lib/$components/$stores aliases — running ./node_modules/.bin/svelte-kit sync fixed path resolution for both tools immediately (dependency-cruiser went from 1 module/0 edges to a correct 388 modules/350 edges; 0 circular deps confirmed independently). But that only fixed part of it. Isolating src/routes/files/[id]/+page.svelte alone (npx madge "src/routes/files/[id]/+page.svelte") shows madge parses it as having zero imports — provably wrong, since line 26 is import TranscriptDisplay from '$components/TranscriptDisplay.svelte', one of ~15 component imports in that file. That single 2,493-line file silently failing to parse is what cascades into most of the false orphans: TranscriptDisplay, VideoPlayer, WaveformPlayer, MetadataDisplay, AnalyticsSection, FileHeader, TagsSection, CommentSection, CollectionsSection, and more are only imported by this one file, so when madge's parser silently drops it, all of them read as unreferenced. dependency-cruiser has the same blind spot for a different reason — it only speaks JS/TS/CoffeeScript, so it can resolve a .svelte file as a valid path but never parses imports from inside one Svelte file's <script> block into another. Neither tool is Svelte-aware enough for this codebase's largest route files. This is a real, confirmed tool limitation — not a code problem, and not something I'd have found without testing the isolated file directly rather than trusting the aggregate orphan count.

10. Backend Module Map explorable docs-site candidate: "backend architecture"

Hand-curated the same way — pyreverse crashes before it can show this layering (root cause below the diagram). This shows what actually matters: routers validate with schemas and call services; Celery tasks call the same services layer, not a duplicate copy of the logic.

Why pyreverse failed here (root cause, confirmed): python -c "import app.api" succeeds cleanly in this venv, and astroid's own modpath_from_file() resolves ordinary files (e.g. app/api/endpoints/files/__init__.py) correctly in isolation. The failure is specific to pyreverse's traversal itself: passing a bare __init__.py as a scan target alongside dotted module names (pyreverse app.api app.services app.tasks app.models) crashes inside astroid/modutils.py's modpath_from_file_with_callback with TypeError: expected str, bytes or os.PathLike object, not NoneType — an upstream astroid/pylint bug in how it mixes path-style and dotted-style scan targets, not a problem in this repo's code. It silently drops every module after the point of failure, which is why only app.models (30 modules) came through intact. The hand-curated Archify diagrams above (2–8) cover the ground pyreverse couldn't reach.

pyreverse also produced a raw field-by-field UML dump of every SQLAlchemy model — dropped from this page: it's a single 2,787px-wide unreadable image with no association lines, worse than just reading backend/app/models/ directly. Not worth keeping just because a tool produced it.
