# v0.5.0 Release Plan — the north star

**Goal:** ship v0.5.0 with working code, real bugs fixed, and every item on the list below
either **completed and verified** or **explicitly deferred with a written reason**.

**Not in scope for v0.5.0:** doc-ingestion (`epic:document-ingestion`) and RAG-quality
(`epic:rag-quality`) work. Those are excluded by decision, not by oversight.

**Working agreement:**
- Opus plans → Sonnet implements → Opus (main chat) reviews → PR.
- Every worktree branch is **merged up from current `master` before the PR runs CI**.
- No new GitHub issues for defects found *while* doing an issue — those are part of that
  issue's definition of done, fixed in the same branch. A genuinely new piece of standalone
  work can still get an issue.
- **Green PRs get merged.** A PR sitting green is not progress.

## ⚠️ The process gap that caused the failed-check emails

**`pre-commit` is NOT the CI check set.** Agents were reporting "both pre-commit tiers exit 0"
and treating that as "CI will pass". It isn't. CI runs these as **separate jobs that
pre-commit never invokes**:

| CI job | Run by pre-commit? | How to run locally |
|---|---|---|
| Run Pre-commit Hooks | ✅ yes (both tiers) | `scripts/safe-precommit.sh run --all-files` + `--hook-stage pre-push` |
| **Backend Tests (pytest)** | ❌ **no** | `cd backend && venv/bin/pytest tests/ --ignore=tests/e2e` |
| **Frontend Unit Tests (Vitest)** | ❌ **no** | `cd frontend && npm run test` |
| **Install paths** | ❌ **no** | `scripts/verify-install-paths.sh` |
| Schema integrity / Docs build | ❌ no | see workflow |

**Required before any push from here on:** both pre-commit tiers **AND** the backend pytest
suite **AND** vitest (when frontend files changed). That is the fix for the email noise.

## ⚠️ The check that kept paying off — run it before EVERY merge

**CI deselects `integration`- and `gpu`-marked tests** (`addopts = -m "not integration and not gpu"`).
So a PR whose value is proven by an integration test can be **fully green while broken**. Caught
twice in one day:

- **#732** — CI green; its integration test actually ran `3 failed, 1 passed, 4 errors`.
- **#733** — CI green; `test_voiceprint_backup_roundtrip.py` is `integration`-marked, so the only
  test proving voiceprints survive a restore **never ran**. Measured: `5 passed in 172.62s`.

```bash
# before merging any PR:
for f in $(git diff --name-only origin/master...origin/<branch> | grep '^backend/tests/.*\.py$'); do
  git show origin/<branch>:$f | grep -cE "pytest.mark.(integration|gpu)"
done
```
Non-zero means CI did not run that file. Run it yourself against a `--fresh` stack.

### ⛔ NEW v0.5.0 BLOCKER — rediarization is broken for every file

Found 2026-09-05 while verifying #666's integration test. **Not filed as a GitHub issue** per
the owner's standing rule — it is release work, fixed in-branch.

```
ERROR app.tasks.rediarize_task:503 Rediarization failed for file <uuid>:
Multi-dimensional indexing (e.g. `obj[:, None]`) is no longer supported.
Convert to a numpy array before indexing instead.
Task rediarize[...] succeeded in 4.35s: {'status': 'error', ...}
```

**It fails quietly** — the Celery task *succeeds* while returning an error payload, so nothing
raises and a user just sees rediarization not work. Any test asserting "the task ran" passes
against this bug.

**Root cause: an unpinned transitive dependency floated under us.**

- We do **not** use pandas. Zero `import pandas` in `backend/app/`; not in any requirements file.
- It arrives from four MANDATORY deps, all declaring a floor with **no ceiling**:
  `pyannote-core`, `pyannote-database`, `pyannote-metrics`, `whisperx` — each `pandas>=2.2.3`.
- pip therefore resolved **pandas 3.0.5**, which **removed multi-dimensional indexing on a
  Series**. pyannote does exactly that: `clustering.py:524`, `vbx.py:125`, `gpu_ops.py:128`,
  `powerset.py:210`.
- **Not a venv artifact** — container and venv both run numpy 2.4.6 / pandas 3.0.5. Production
  is affected identically.

**This is issue #492's lesson recurring on a transitive dep.** `backend/CLAUDE.md` already says
"a floor is a version number but not a pin" — that was applied to every *direct* dependency, and
pandas is not direct, so nothing pinned it. Same shape as the nltk `pathsec` breakage.

**Fix: pin pandas to the 2.3.x line**, in `requirements.txt` **and** the sibling files
(`-lite`, `-ci`, `-test`) so venv, prod image, lite image and CI resolve identically. Verified
nothing mandatory needs pandas 3 (the only `pandas==3.0.1` is `mmh3`'s optional `plot` extra,
not installed). Adding a first pin with a ceiling is what the rule prescribes — it is **not** the
prohibited "downgrade an existing pin to reproduce a result".

**Polars is not an option** and was considered: we use zero pandas ourselves, so there is nothing
of ours to migrate. The dependency is pyannote's and whisperx's internal choice; switching would
mean forking both.

## 719 scope gap — read before calling it done

PR #730 implements the **test-harness** device guard: the backend suite no longer opens CUDA
contexts on every visible GPU. That is what issue #719 asks for and it is verified (mutation
test: naive substring predicate → 7 failures, the guard catches it).

**It does NOT make gpu-scale / shared-GPU work correctly at runtime, and it does not make the
runtime respect the env file.** That is a separate requirement. Concretely still open:
- The released `-m gpu` state does not pin to `GPU_DEVICE_ID` — the gate's GPU phase leaves all
  cards visible, and CUDA device 0 there is a **reserved** card.
- Measured on this host: **CUDA's default ordering does not match `nvidia-smi`** —
  `CUDA_VISIBLE_DEVICES=1` selects nvidia-smi GPU **2**. #730 sets `CUDA_DEVICE_ORDER=PCI_BUS_ID`
  for the test harness only; the **runtime** has no such guarantee.
- `GPU_SCALE_DEVICE_ID` (default 2) vs the sidecar's `DIAR_NATIVE_GPU:-${GPU_DEVICE_ID:-0}` —
  a cross-card arrangement is legal and merely slower, and has never been re-examined.

**Action:** land #730 as-is (it is correct for its scope), then a **separate unit** for runtime
GPU device selection + env-file respect, which is also the precondition for #711.

## Known fragile test — fix before the release gate

`backend/tests/unit/test_opentr_fresh_diar_native_models_isolation.py::
test_fresh_deployment_leaves_the_live_export_directory_completely_untouched`
**hardcodes `--port-offset 200`.** Any developer (or agent) holding a `--fresh` stack at that
offset makes it fail:

```
❌ Cannot start fresh deployment 'audit2' with --port-offset 200 — already bound:
   5373 5374 5375 5376 5377 5378 5379 5380 5381 5383
```

That is `opentr.sh`'s collision guard working correctly and the test refusing correctly — but it
means the test measures the environment as much as the code, and it will fail the release gate
whenever a stack happens to be up. Fix: have it pick a free offset dynamically.

Observed 2026-09-05 during the post-merge sanity run on `master` — it was the ONLY failure across
`tests/unit` + `tests/api`, and it was environmental, not a regression from the nine merges.

## Gotcha that cost real time — do not repeat

**`.env` is gitignored, so `git worktree add` never copies it.** A `--fresh` stack started
from a worktree fails with `POSTGRES_PASSWORD` unset. Two agents hit this and one gave up on
its verification because of it. Fix: `ln -sf /mnt/nvm/repos/transcribe-app/.env .env` in the
worktree. It stays gitignored; never read or commit it.

**Throwaway red/green-check files go in `/tmp`, never a sibling directory inside the
checkout.** Two stray `PlyrMiniPlayerAudit*.test.ts` files were left in the shared main
checkout, where whole-tree frontend checks pick them up.
