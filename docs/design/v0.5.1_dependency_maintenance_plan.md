### Why #932 and #803 stay as ONE PR each (revised from an earlier draft of this plan)

An earlier pass of this plan proposed manually splitting #932 into 3 PRs and #803 into 2, to
isolate the risky packages (`sentence-transformers`, `typescript`, `vitest`) from routine churn.
**That's the wrong trade for this repo and has been dropped.** Two reasons:

1. **The 7-PR shape already IS the deliberate grouping** — `.github/dependabot.yml`'s `groups:`
   blocks (backend, frontend, github-actions, docs-security, docs, frontend-security,
   frontend-docker) are what produced these 7 PRs, one per ecosystem/group, on a weekly schedule.
   Manually re-splitting one of those groups is a **one-time, throwaway** fix — Dependabot
   regenerates the same 42-package grouped PR again next week from the same config, so hand-split
   branches don't change anything going forward. It's extra branches/PRs/CI runs for a benefit
   that evaporates in a week.
2. **This repo already has the correct sustainable mechanism for "this package is too risky to
   batch"**, and it's not manual splitting — it's `dependabot.yml`'s per-package `ignore:` block
   (see backend's `ignore:` entries for `torch`, `transformers`, `websockets` majors, each with a
   one-line reason). If a package proves troublesome, carve it out **there**, once, so Dependabot
   itself opens it as a separate PR every future week. That is the actual "best practice" version
   of what hand-splitting a PR is trying to achieve.

So: **merge #932 and #803 each as a single PR**, but don't merge blind — check out each PR branch
locally and run the risk-scoped verification below *before* merging, same rigor as before, just
without manufacturing extra branches to hold it. If `sentence-transformers` (or `typescript`/
`vitest`) turns out to be broken, the fix is either (a) fix forward in that same PR before merging
it (see the "if something breaks" section below), or (b) add that one package to `dependabot.yml`'s
`ignore:` with a written reason and re-push the PR with just that package reverted in the
lockfile/requirements file — never a fresh hand-split branch.

## Execution model: ONE consolidated branch/PR, not 7 separate merges

Per direction: condense further. All dependency work lands as a sequence of **merge commits on
one branch**, `chore/v0.5.1-dependency-maintenance`, tested progressively as each Dependabot
branch is merged in — not as 7 individually-merged GitHub PRs. One PR opens from that branch into
`master` at the end. This still satisfies root CLAUDE.md's "never squash, preserve history" rule:
`git merge --no-ff origin/dependabot/<branch>` per group keeps each Dependabot branch's own commits
intact inside the consolidated branch's history, so `git log --first-parent` on the final PR still
shows exactly which merge brought in which group — bisectability is preserved without needing
separate PRs to get it.

Each of the 7 Dependabot branches is merged in **one at a time**, in risk order (cheapest first),
with the scoped verification for that group run **immediately after that merge, before merging
the next one** — so a break is caught and fixed at the commit that caused it, not discovered later
in a pile of 7 merges. The 7 upstream Dependabot PRs (#813/#687/#926/#507/#932/#803/#677) each get
closed with a comment pointing at the consolidated PR once it's open, per this repo's "close with
a written reason" convention — GitHub's "Closes #N" only works for one issue per keyword, so use
it once per PR reference or list them explicitly in the closing comment.

The 3 release-pipeline issues (#937/#938/#939) are a **different concern** (release-script bugs,
not dependency bumps) and stay on their own branch/PR — folding them into the dependency branch
would mix unrelated changes in one diff for no benefit.

## Efficiency — avoiding redundant work

The naive version of this plan re-runs the full gate, a rebuild, and a manual ASR pass after
*every* one of the 13 PRs, which is the wrong shape for a 13-PR batch — most of that cost is
pure waste for a low-risk patch bump. The plan above is deliberately structured to spend the
expensive checks exactly where the risk is and nowhere else:

| Check | Cost | Run when | Not when |
|---|---|---|---|
| `npm run build` (docs-site) | ~seconds | Once per Phase-1 sub-batch (#926+#507 share one check, since both touch the same lockfile) | Not after #813 (no docs-site touch) |
| `npm run check && npm run build` (frontend) | ~1-2 min | Once after 3a, once after 3b | Not after 3c (Docker-only change, different check) |
| `./opentr.sh rebuild-backend` + parity check | ~5-10 min (image rebuild) | Once, at the **end** of Phase 2 (all of 2a/2b/2c merged) | Not after each of 2a/2b/2c individually — the container only needs to reflect the *final* state before parity matters |
| ASR/RAG manual smoke | ~5 min hands-on | Once, in Phase 5, after everything is merged | Not per-PR in Phase 2 — 2b is the only sub-PR that plausibly changes ASR behavior, but the full end-to-end pass in Phase 5 covers it more cheaply than re-transcribing after every merge |
| Full `run-integration-tests.sh` gate | ~15-30 min | Once, in Phase 5 | Never mid-phase — this is explicitly what #940's acceptance criteria says ("not per-PR, the gate is the point") |
| Full `run-e2e.sh` (all markers) | ~10-20 min | Once, in Phase 5 | Not for every frontend PR — 3a/3b already get the cheaper `npm run check`/`build`/`test` loop; the full browser E2E is reserved for the final assembled state |
| `release.sh rehearse` (fresh-install + upgrade) | ~20-40 min | Once, as part of the real `release.sh run 0.5.1` in step 7 | Never speculatively mid-plan — it requires the live stack stopped and is the most expensive check in the whole plan |

The one place where **more** checking than "just merge it" is deliberately paid for, not saved
on, is Phase 2b (ASR/embeddings) and Phase 3b (TS/vitest majors) — those get PR-scoped manual
verification in addition to the batch-level Phase 5 pass, because they are the two places a
regression could be masked by everything *else* in the batch working, and because catching a
regression at the PR that caused it (bisection for free) is far cheaper than catching it only in
the Phase 5 aggregate and then bisecting across 13 merged PRs to find which one broke it.

## If something breaks — rollback / bisection

- **A single sub-PR fails its own scoped check** (e.g. 2b's ASR smoke test regresses, or 3b's
  `svelte-check` surfaces new TS 7 errors): fix forward within that PR before merging — per this
  repo's "fix, don't defer" convention, a regression found while verifying a change is fixed in
  that same change, not filed as a follow-up and merged anyway. Do not merge a PR whose own
  scoped verification step failed.
- **Phase 5's aggregate gate fails after all 13 PRs are merged, and the specific cause isn't
  obvious**: bisect by manifest, not by PR-count — Phase 2/3's split already gives you 6 scoped
  merge commits (2a/2b/2c, 3a/3b/3c) plus 4 Phase-1 merges, so `git log --oneline` on the branch
  directly names candidate commits; there is no need for a binary search across 42+17 individual
  package bumps because the split was designed to make each commit independently revertible.
- **Never merge a Phase-5 fix that widens a type or silences a check to make the gate pass** (per
  root CLAUDE.md's "fix the finding, never silence it") — a TS 7 or vitest 5 upgrade that requires
  `// @ts-ignore` or a loosened assertion to go green is not actually verified; either fix the
  real code issue or hold that specific sub-PR (3b) out of the v0.5.1 batch and file it as its own
  follow-up issue rather than let it block or fake-pass the whole release.
